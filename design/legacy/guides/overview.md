# Worldgen Authoring Pipeline: Overview

## What This Is

A 10-step pipeline for generating evaluation domains. An LLM (Claude Code)
authors a **world** — entities, fields, relationships, gates, rules, seed data —
across 9 verified steps. Tasks are then generated **by graph traversal**: pure
code, no LLM, solvable by construction.

Total LLM authoring: ~450 lines across 9 steps. Each step is constrained by
all previous steps. Tasks are mechanical consequences of the world's topology.


## Five Design Principles

1. **Small authoring surface per step** — each step produces a small, well-typed artifact
2. **Narrowing funnel** — each step's output constrains the next step's input space
3. **Verify-then-proceed** — code verification gates between every step; on failure, retry just that step
4. **Derive, don't author** — anything derivable from earlier steps is derived mechanically
5. **Retry is narrow** — on failure, re-generate just the failing step with error feedback

## How Gates Create Depth

Gates are the core mechanism. A gate on an edge means: a field on the source
entity must have a specific value before the agent can traverse to the target entity.

```
Customer ──[account_status == "active"]──> Order ──[status != "cancelled"]──> OrderItem
```

If `account_status` is broken ("suspended"), the agent can't see Orders.
If `order.status` is broken ("cancelled"), the agent can't see OrderItems.

**Depth = number of sequential gates from entry point to deepest perturbation.**

The agent must fix gates in order: fix account_status (depth 1) to discover
order.status is wrong (depth 2) to discover OrderItem.quantity is wrong (depth 3).

Progressive disclosure, dependency chains, and multi-step reasoning all emerge
from gate placement — no hand-authored dependencies needed.


## How Tasks Are Generated by Traversal

The "break deep first" trick:

1. Start from a valid world state (seed data, all normal values)
2. Pick a node at target depth — break a field on it
3. Work backward toward the entry point — break gate fields that hide the deep break
4. The broken state IS the task; reversing the breaks IS the solution

```
Generate depth-3 task:
  1. Break OrderItem.quantity = 0          (deep — hidden behind two gates)
  2. Break Order.status = "cancelled"      (gates OrderItem)
  3. Break Customer.account_status = "suspended"  (gates Order)

Agent's solution path (forward):
  1. Fix account_status → can now see Order
  2. Fix order.status → can now see OrderItems
  3. Fix quantity → done
```

**Solvability is guaranteed by construction**: the task was created by valid
operations from a valid state, so reversing those operations is always possible.


## Generality: 8 World Types

The same model handles fundamentally different agent patterns:

| World                | Gate Types         | Actors          | Novel Challenge                    |
|----------------------|--------------------|-----------------|------------------------------------|
| Customer Service     | property + actor   | agent + user    | Progressive disclosure via gates   |
| Personal Assistant   | actor + info       | agent + user    | Cross-service references           |
| SRE / Infrastructure | property           | agent only      | Deep diagnostic chains             |
| Data Pipeline        | property           | agent only      | Effect-to-cause tracing            |
| HR Onboarding        | actor + property   | agent+user+3sim | Multi-actor coordination           |
| Research Analysis    | property + actor   | agent + user    | Information synthesis, few writes  |
| Calendar Scheduling  | actor + property   | agent + user    | Constraint satisfaction, computed  |
| Spreadsheet          | property           | agent (or +user)| Grid structure, computed goals     |

Same model for all: **graph + gates + tools + rules + projections**.
The gate type mix drives diversity. User sim is just another actor gate.


## What the LLM Authors vs. What Code Does

**LLM authors the WORLD** (creative, semantic):
- Steps 1-5: What entities exist, their fields, how they connect, what constrains them, realistic data
- Steps 6-9: Custom tools, projections, what can break, how the agent should behave

**Code does EVERYTHING ELSE**:
- Derive standard tools from schema (step 6)
- Generate tasks by graph traversal (step 10)
- Compose compound tasks
- Verify solvability (construction guarantee + oracle simulation)
- Verify composition safety (field/tool exclusivity)
- Render to format-specific output

The world is the creative artifact. Tasks are mechanical consequences of the world.


## How to Use These Guides

Read the guide for each step **before** authoring that step's artifact. Each guide tells you:
- Exactly what types to produce (with field-level documentation)
- What's locked from prior steps (what you CANNOT change)
- 2-3 concrete examples from different world types
- Anti-patterns to avoid
- What verification checks and how to fix common failures
